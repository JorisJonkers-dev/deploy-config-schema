## Blocking unknowns

The lens requires the target k3s version, node count and datastore before judging. Two of the three are not determinable from this repository, and that absence is itself the first finding.

| fact | status |
|---|---|
| **k3s version** | **Not determinable.** No pin anywhere — no `.tool-versions`, no `kubeVersion`, no CI matrix, no field in `schemas/platform.schema.json`. `kind: k3s` (`fixtures/platform/full-tree.platform.yaml:6`) is the whole declaration. |
| **Node count** | **Determinable, and it is one control-plane node.** Every fixture has exactly one host carrying `k3s-control-plane`: `single-node.platform.yaml:30`, `full-tree.platform.yaml:42`, `multi-site.platform.yaml:37`. Worker count is 1–2. |
| **Datastore** | **Not determinable, and not expressible.** Repo-wide grep for `etcd`, `sqlite`, `datastore`, `cluster-init` returns nothing outside Gatus's own app config and a passing mention of etcd in `docs/adr/0005:148`. There is no field for it in any schema. |

k3s defaults to embedded SQLite for a single server and cannot run more than one server on it ([docs.k3s.io/datastore](https://docs.k3s.io/datastore)); embedded etcd requires `--cluster-init` and three servers ([docs.k3s.io/datastore/ha-embedded](https://docs.k3s.io/datastore/ha-embedded)). With one control-plane node and no `--cluster-init` anywhere in the tree, **embedded SQLite is the only configuration consistent with the fixtures**, and I treat it as the working assumption throughout. Every finding that turns on it is marked.

No finding below rests on the k3s *version*: the API versions in use (`apps/v1`, `batch/v1`, `policy/v1`, `autoscaling/v2`, `networking.k8s.io/v1`, `monitoring.coreos.com/v1`, `traefik.io/v1alpha1`, `secrets.hashicorp.com/v1beta1`, `kustomize.toolkit.fluxcd.io/v1`, `helm.toolkit.fluxcd.io/v2`) are all current and none is deprecated or removed on any k3s release still supported. **There is no API-drift finding to report and I am not inventing one.**

**Standing assumption, stated once.** `spec/v1/00-overview.md:3` says the v1 branch touches nothing under `src/`, `schemas/` or `fixtures/`. So the code is the shipped v0.22 renderer and the spec is the proposed v1. Where a finding is a disagreement between them I say which side is which; where a finding is "the spec describes a mechanism that no code implements", that is stated as a gap in the spec's evidence, not as a bug in v0.22.

## Does this need Kubernetes at all?

The case against, concretely, before any manifest.

The estate is **one control-plane node plus one or two workers**, and the fixtures say what runs on it: a frontend, an API, a Postgres, Jellyfin, and a foundation of cert-manager, external-dns, two Traefiks, MetalLB and VSO. `spec/v1/50-lifecycle.md:33` counts the whole thing at **405 objects for ~30 Services**, of which **41 are the foundation that exists only to make the other 364 possible**. That is a ten-percent overhead paid in objects; in operational terms it is higher, because the foundation is the part with the CVEs, the CRD upgrades and the API deprecations.

Every property Kubernetes is bought for is absent here:

- **Rescheduling on node loss** does not work. `docs/adr/0008:41` — *"Storage is `local-path`, not Longhorn: all fourteen PVCs are `ReadWriteOnce`"*. A `local-path` volume does not survive its node ([docs.k3s.io/add-ons/storage](https://docs.k3s.io/add-ons/storage)), so every stateful workload is pinned to one machine by construction. `spec/v1/20-resolved-deployment.md:160` concedes this: the binding is *"existing cluster state — observed, not decided"*, and moving it *"requires a state-move-plan rather than a re-render"*. A scheduler that cannot move your stateful workloads is a scheduler you are paying for and not using.
- **Horizontal scale** is not exercised. `spec/v1/10-service-intent.md:508` records that `auth-api`'s two replicas *"were a capacity decision on freed Frankfurt budget, not an availability requirement"*. On a single node, two replicas is two processes on one kernel.
- **Control-plane HA** is not present and cannot be, on the assumed datastore.
- **Declarative config, drift correction and rollback** — the three things this repository actually cares about — are all supplied by the *tooling around* Kubernetes (OCI fragments, a lock, server-side apply, a re-apply CronJob), not by Kubernetes. The same three could sit on top of systemd units and a `podman-systemd` generator, or on Nix, which `docs/adr/0010:48` says the estate **already runs as a second deployment target** for `samba`, `wolf`, `tailscale`, `media-storage` and `btrfs-backup-snapshots`.

That last point is the sharpest form of the argument: the estate is already maintaining two deployment mechanisms, and `docs/adr/0010:54` rejects modelling the Nix one because *"rendering NixOS is not writing a file but producing a build and an activation, and it would have made v1 an order of magnitude larger."* The alternative that was never argued is the reverse — collapse onto the target that already handles host-level services, and delete 41 foundation objects, two Traefiks, MetalLB, VSO, Flux, keel and the CRD upgrade treadmill along with them.

**Is Kubernetes justified anyway? Yes, but by exactly two things, and they should be named so the rest can be judged against them.**

1. **The API server as the authorisation boundary.** `spec/v1/50-lifecycle.md:200` — *"a workflow that tries to apply a Service it does not own receives a 403 rather than producing a bad deploy."* Nothing on a plain host gives you a per-aggregator authorisation surface for free. (K3S-013 finds that this specific claim does not hold as rendered — but the *shape* of the argument is sound and it is the strongest one available.)
2. **Server-side apply field ownership as the drift mechanism.** `spec/v1/50-lifecycle.md:151` — a conflict *"means a human edited a field this aggregator owns: it is reported, never resolved with `--force-conflicts`."* That is a genuinely hard thing to build, it is the load-bearing property of the whole delivery model, and Kubernetes gives it to you.

Everything else — scheduling, rescheduling, scaling, HA, service discovery across nodes — is either unused or actively worked around. **The design should be judged as "a declarative object store with field-level ownership and an authorisation boundary, that happens to also run containers."** Judged that way, most of the findings below are about paying the container-orchestrator's costs without taking its benefits.

## Findings

### K3S-001 — One k3s server, an unnamed datastore, and no restore path for either the cluster or its data
Severity: Blocker
Confidence: Likely (the SQLite assumption is stated above; the single control-plane node and the absent backup are Certain)
Target: `fixtures/platform/full-tree.platform.yaml:8`; `src/validator.ts:97`; `spec/v1/60-setup.md:141-156`

Evidence:
```
  bootstrap: alpha-control-1
  } else if (!node.target_roles.includes("k3s-control-plane")) {
```

Problem: The model has one field for the control plane — a single `bootstrap` host — and one validation, that the named host carries the role. There is no field for the datastore, no field for a server count, and `validateCluster` never checks how many hosts carry `k3s-control-plane`, so a second one is expressible and would produce a cluster that cannot start on the assumed SQLite backend. Under that assumption the entire estate — API server, datastore, all fourteen `local-path` PVs, the self-hosted runner that applies changes (`spec/v1/examples/workflows/aggregator-deploy.yml:44`, `runs-on: [self-hosted, k3s-prod]`) and the CronJob that corrects drift — sits on one machine, and the recovery tooling is inside the thing it recovers. `spec/v1/60-setup.md`'s pre-flight checklist has seven items and not one of them is a backup or a restore; the only rehearsal it demands is *"a break-glass rollback has been rehearsed"* (`:156`), which re-applies a lock and restores no data.

Consequence: The control-plane node dies. There is no etcd snapshot because there is no etcd; there is no SQLite backup because nothing anywhere takes one; there are no PV snapshots because `docs/adr/0008:43` says *"`local-path` has no CSI snapshot support"*. The estate is rebuilt by hand from OCI fragments, and every byte of Postgres, Gatus, Grafana, Loki and the `irreplaceable`-classed knowledge vault is gone. In six months this reads as a homelab that documented its rollback story in four places and its restore story in none.

Direction: The datastore and the server count belong in `platform.schema.json` as declared facts, and the pre-flight checklist needs a *restore*, rehearsed, before the first production apply.

### K3S-002 — Every foundation chart is pinned to `*`
Severity: Blocker
Confidence: Certain
Target: `src/adapters/flux-utils.ts:615, 624, 641, 665, 679, 687`

Evidence:
```
    CERT_MANAGER_CHART_VERSION: "*",
    TRAEFIK_PUBLIC_CHART_VERSION: "*",
```

Problem: Every class-B chart default — cert-manager, external-dns, both Traefiks, MetalLB, VSO — is `"*"`, and the matching `HelmRepository` interval is `1h`. A Flux `HelmRelease` with `version: "*"` resolves to the newest chart in the repository on each reconcile, so the foundation upgrades itself, unattended, across majors, on an hourly poll. This is the same foundation `spec/v1/50-lifecycle.md:41-47` describes as *"the foundation everything else stands on"* and deliberately excludes from the aggregator gate, so none of it is tested by anything.

Consequence: A cert-manager or Traefik major lands at 03:00 on the single node that terminates all public TLS. `spec/v1/20-resolved-deployment.md:138` promises image references are *"a digest, never a tag"* and `:173` promises re-rendering is byte-reproducible — both hold for the 364 objects that do not matter and neither holds for the 41 that do. The document that is lying is chapter 20's determinism section: it describes the reproducibility of the render, and is read as the reproducibility of the cluster.

Direction: Class B needs the same pinning discipline as class A, or the class-A/class-B boundary needs to stop being described as a safety property.

### K3S-003 — No securityContext and no resource requests are rendered, and layer 1 has no vocabulary to add them
Severity: Blocker
Confidence: Certain
Target: `src/deployment/render/workloads.ts:130-175`; `spec/v1/10-service-intent.md:503-508`

Evidence:
```
2. **`size`.** Requests and limits draw on finite node capacity, so rule 2 forbids
   declaring them. Proposed as a closed class mapped by the cluster context,
```

Problem: `container()` builds a container from name, image, pullPolicy, ports, command, args, env, envFrom, volumeMounts, probes and resources — and stops. A repo-wide grep for `securityContext`, `runAsNonRoot`, `readOnlyRootFilesystem`, `allowPrivilegeEscalation` and `seccompProfile` across `src/` and `schemas/` returns **zero hits**. Every pod this tool renders runs as whatever UID the image declares, with `allowPrivilegeEscalation` defaulted true, a writable root filesystem and the default capability set. `resources` is emitted only when the model already carries it, and `size` — the field that would supply it — is explicitly ungraded. So the standing state is BestEffort QoS for the whole estate.

Consequence: On a single node this is not a policy problem, it is an availability one. The k3s server process, the SQLite datastore and every application pod share one kernel with no reservation between them; one leaking BestEffort container drives node memory pressure and the kubelet evicts from a pool where every candidate has identical priority. The security half is worse to fix later: adding `runAsNonRoot` is a layer-1 change, and layer 1 is authored by hand in ~30 separate repositories (`spec/v1/10-service-intent.md:4`). Retrofitting is thirty pull requests and a coordinated image rebuild.

Direction: `size` and a pod hardening class need grading before the first production apply, not after — they are the two fields whose absence cannot be corrected from the platform side.

### K3S-004 — "Default-deny NetworkPolicy in audit mode" is not a thing that exists on this stack
Severity: Major
Confidence: Certain
Target: `docs/adr/0011-dependency-edges.md:34`; `spec/v1/60-setup.md:153`

Evidence:
```
- **Default-deny must ship in audit mode first.** Any connection that exists but
- [ ] default-deny NetworkPolicy is in **audit** mode, not enforce
```

Problem: The Kubernetes `NetworkPolicy` API has no audit, dry-run or log-only mode — a policy is enforced the moment it selects a pod. k3s enforces NetworkPolicy with an embedded kube-router netpol controller ([docs.k3s.io/networking/networking-services](https://docs.k3s.io/networking/networking-services)), which programs iptables and ipsets and has no audit mode either. Policy audit mode is a Cilium and Calico feature, and neither is in this estate's pack set (`fixtures/platform/full-tree.platform.yaml:26-31`: cert-manager, external-dns, traefik×2, metallb, vso). The ADR states the audit stage as the mitigation for a risk it correctly identifies — *"this cluster is known to contain undeclared paths"* — and `60-setup.md:153` makes it a hard precondition for the first production apply.

Consequence: The precondition can never be marked done, so either the checklist is quietly ignored (and default-deny lands as enforce, cutting the undeclared paths the ADR warned about, on a single node with no second control plane to debug from) or the whole delivery model waits on a CNI swap nobody has scoped. ADR-0011 is the document that is lying, and it is lying about its own safety net.

Direction: Either the CNI decision moves ahead of the default-deny decision, or the audit stage is replaced with something the stack can actually do — flow logs off the existing Alloy/Loki pack, for instance.

### K3S-005 — Every rendered egress policy silently blocks DNS
Severity: Major
Confidence: Certain
Target: `src/deployment/render/networkpolicy.ts:86-102`

Evidence:
```
      policyTypes: ["Egress"],
      egress: [{ to: [{ namespaceSelector: …, podSelector: … }],
```

Problem: `providerPolicy` emits a policy whose only egress rule is to the provider's pod. Once any policy with `policyTypes: [Egress]` selects a pod, all egress not matched by a rule is denied — including UDP/TCP 53 to `kube-dns` in `kube-system`. There is no DNS allow rule anywhere in this file. The consumer therefore cannot resolve the provider's own `svc.cluster.local` name, which is the address the coordinate derivation hands it.

Consequence: The consumer starts, resolves nothing, and fails with a DNS timeout rather than a connection refused — so it is diagnosed as "Postgres is down" or "the service mesh is broken" rather than as a policy that was rendered too tightly. On a single node with no second environment, this is diagnosed in production. It also means the *first* egress policy this tool ever renders takes the workload offline, which will teach the estate that the network-policy feature is broken and should be left off.

Direction: A DNS allow belongs in the derivation itself, not in each service's declaration — it is the canonical case for a value that is derived rather than authored.

### K3S-006 — The ingress policy admits the edge namespace and nothing else, including Prometheus
Severity: Major
Confidence: Likely (depends on the metrics stack scraping from its own namespace, which `docs/adr/0012:32` implies via `release: metrics-stack`)
Target: `src/deployment/render/networkpolicy.ts:48-53` and `src/deployment/render/servicemonitor.ts:41-51`

Evidence:
```
      policyTypes: ["Ingress"],
      ingress: [{ from: [{ namespaceSelector: { matchLabels: { "kubernetes.io/metadata.name": … ingress_intent.defaults.namespace } } }],
```

Problem: The same renderer emits, for one workload, an ingress policy admitting only the edge namespace on the routed ports, and a `ServiceMonitor` telling Prometheus to scrape that workload on the metrics port. The two are produced by sibling files with no shared constraint, and the policy has no rule for the monitoring namespace and no rule for the metrics port. Nothing in the codebase cross-checks a rendered `NetworkPolicy` against a rendered `ServiceMonitor`.

Consequence: The scrape target goes `down`, which Prometheus reports as an instance failure rather than as a policy denial. `docs/adr/0012:20` already documents the estate's history here — *"Gatus monitors 41 endpoints and notifies nobody"* — and this reproduces the same class of silent hole from the other side: a workload that is monitored, alerting-routed, and unreachable by the scraper. It also breaks the Gatus internal-probe path (`src/deployment/render/gatus.ts:78-82`), which dials the service DNS name from the `observability` namespace.

Direction: The scrape surface and the status probe are inbound edges too; if the edge set is meant to be complete (ADR-0011), they belong in it.

### K3S-007 — Two LoadBalancer implementations and a hostPort collision, on a k3s cluster whose bundled components are never disabled
Severity: Major
Confidence: Likely (Certain that nothing disables them in this repo; the k3s server flags may live in the unreviewed `nix-config`)
Target: `src/adapters/flux-utils.ts:643, 647-648`; `test/fixtures/blueprint-packs/packs/flux-core/traefik-public/release.yaml:49-53`

Evidence:
```
    TRAEFIK_PUBLIC_SERVICE_TYPE: "LoadBalancer",
    TRAEFIK_PUBLIC_WEB_HOST_PORT: 80,
```

Problem: Three things want the same node ports. k3s ships ServiceLB (klipper) and a packaged Traefik by default, both of which take 80/443. This estate installs MetalLB *and* a second Traefik whose Service type is `LoadBalancer` *and* which additionally binds `hostPort: 80`/`443` directly. A repo-wide grep for `--disable`, `servicelb` and `klipper` across `src/`, `docs/`, `spec/`, `fixtures/` and `README.md` returns nothing — there is no k3s server configuration in this repository at all. MetalLB's own guidance is that ServiceLB must be disabled first; two LoadBalancer controllers otherwise both act on the same Service.

Consequence: On a fresh bootstrap the klipper `svclb-*` pod cannot bind 80/443 because Traefik's hostPort already holds them, so it sits `Pending` or crash-loops; the Service may never receive an external IP, and `external-dns` then publishes a record for an address that answers nothing. Because the annotation-driven DNS target (`flux-utils.ts:645`) is set independently, DNS looks correct while the ingress is dead — the failure presents as "the site is down" with a green Flux and a green DNS record.

Direction: The k3s server flags are part of the platform contract and belong in the same declared model as the node roles; today they are somewhere this repository cannot see.

### K3S-008 — Public ingress is one replica with a rollout strategy that guarantees an outage window
Severity: Major
Confidence: Certain
Target: `test/fixtures/blueprint-packs/packs/flux-core/traefik-public/release.yaml:17-24`

Evidence:
```
      replicas: 1
        maxSurge: 0
```

Problem: `replicas: 1` with `maxSurge: 0, maxUnavailable: 1` means the only ingress pod is terminated before its replacement exists, let alone becomes Ready. The `hostPort: 80/443` on the same chart makes `maxSurge: 1` impossible anyway — two pods cannot bind the same port on the same node — so the outage is structural, not a misconfiguration. Meanwhile `docs/adr/0008:18-24` describes `maxSurge: 1, maxUnavailable: 0` as the estate's hard-won zero-downtime pattern for applications, and records what it cost to learn: *"under `Recreate` every image roll opened a zero-pod window, so a slow cold start or a flaky ghcr image pull took the MCP fully down (503)"*.

Consequence: Every chart bump, node reboot and pod eviction takes **all** public HTTPS down for the pull-plus-start duration — and per K3S-002 those bumps arrive unattended and unpinned. The estate spent real effort eliminating the zero-pod window for individual applications and left it in place on the single component that fronts all of them. The application-level `maxUnavailable: 0` becomes decorative: the pod stays up while the thing that routes to it does not.

Direction: This is the one component where a second node earns its cost; if there is not going to be one, the ingress outage window should be a stated number rather than an accident.

### K3S-009 — Placement renders the archived label prefix, and collapses a required capability into a site match
Severity: Major
Confidence: Certain
Target: `src/adapters/flux-utils.ts:957-962`; `test/fixtures/kubernetes-parity/postgres-derived.yaml:13`; `src/deployment/render/workloads.ts:340-352`

Evidence:
```
  if (entry) return { key: `${platform.name}/site`, value: entry[1].site ?? "default" };
        personal-stack/site: frankfurt
```

Problem: Three separate things go wrong in the same code path. First, `firstHostSelector` is asked for the host with capability `public-ingress` and then **discards the capability**, returning a selector on that host's *site* — so a workload requiring a capability is placed on any node in the site, whether or not it advertises it, and nothing validates that only one node per site holds it. Second, the label prefix is `platform.name`, which the fixtures set to `personal-stack` — the prefix `docs/adr/0009:26-28` says is *"named after `ExtraToast/personal-stack`, an **archived** repository that rejects pushes"* and must be retired. Third, `workloads.ts` uses `${clusterName}/capability-…` in one branch and hardcodes `platform.jorisjonkers.dev/node-id` in the GPU branch, so one function emits two label schemes. `spec/v1/20-resolved-deployment.md:239` shows the intended output as `platform.jorisjonkers.dev/capability-public-ingress`. The renderer is the truth; chapter 20's worked example is describing a renderer that does not exist.

Consequence: A site-level selector plus a `local-path` PV is a reschedule deadlock. The PVC binds to a PV on node A; when the pod is evicted and the scheduler picks node B in the same site, the pod sits in `ContainerCreating` indefinitely because the volume is not there — the exact failure `docs/adr/0009:55-57` claims the resolver prevents by pinning to the node. And ADR-0009's own thesis — that an unsatisfiable *preference* is a build error because *"an unsatisfiable preference is silently ignored, so it read as GPU-aware placement while doing nothing"* — is undone by a `requires` that quietly becomes a site match.

Direction: The capability has to survive into the selector, and one label prefix has to win before anything is rendered against either.

### K3S-010 — One field means both "roll with no gap" and "never allow a drain"
Severity: Major
Confidence: Certain
Target: `src/deployment/render/workloads.ts:291-302` and `:434-443`

Evidence:
```
  if (workload.rollout.maxUnavailable !== undefined) spec.maxUnavailable = workload.rollout.maxUnavailable;
      maxUnavailable: workload.rollout.maxUnavailable ?? 0,
```

Problem: `workload.rollout.maxUnavailable` feeds two objects with opposite meanings. In `deploymentStrategy` it is the rolling-update surge control, where `0` is the desired zero-downtime setting ADR-0008 documents. In `pdbManifest` it becomes `PodDisruptionBudget.spec.maxUnavailable`, where `0` means *no pod may ever be voluntarily evicted*. A service declaring the estate's standard zero-downtime rollout therefore also declares that its pods can never be drained.

Consequence: `kubectl drain` on the single node hangs forever, and so does anything that uses the eviction API — node upgrades, kernel patches, k3s upgrades. Because the PDB is only rendered when the field is set, this is invisible until the first time someone tries to reboot the machine, at which point the fix is to delete PDBs by hand on a cluster with no second control plane. On a one-node cluster a `maxUnavailable: 0` PDB is close to meaningless as protection and total as an obstruction.

Direction: These are two decisions wearing one name; `spec/v1/10-service-intent.md:508` already flags `minAvailable` as ungraded, and this is the reason it cannot be graded as a synonym.

### K3S-011 — "An RWO volume forces `Recreate`" is documented as derived and is authored
Severity: Major
Confidence: Certain
Target: `src/deployment/render/workloads.ts:434-435`; `docs/adr/0008:33-34`; `spec/v1/20-resolved-deployment.md:141`

Evidence:
```
  if (workload.rollout.strategy === "recreate") return { type: "Recreate" };
| rollout strategy, surge, unavailability | `zeroDowntime`, `volumes` | an RWO volume forces `Recreate` |
```

Problem: Both documents state the derivation as a rule the platform applies — ADR-0008 with a count (*"the strategy split is 21 `Recreate` to 9 `RollingUpdate`, and `Recreate` is forced wherever a `ReadWriteOnce` volume cannot attach to two pods at once — so strategy follows from volumes"*). The renderer reads a declared enum (`src/schemas/service-intent.ts:168`) and defaults everything else to `RollingUpdate` with `maxSurge: 1`. Nothing anywhere inspects `workload.storage.volumes` to choose a strategy; grep for `Recreate` across `src/` returns two call sites, both reading the authored field.

Consequence: A stateful workload whose author forgets `strategy: recreate` gets `maxSurge: 1, maxUnavailable: 0` against an RWO volume. On a single node the two pods happen to co-schedule and it works, hiding the defect; the moment a second worker exists, or the pod is rescheduled across nodes, the new pod blocks on volume attachment while the old one holds it and `maxUnavailable: 0` forbids removing it — a rollout that hangs until the progress deadline and then reports failure without ever having been able to succeed. Both documents are lying, and they are lying about the derivation ADR-0008 uses as its headline example of "hard-won behaviour turned into a rule".

Direction: The claim is testable in one assertion; either write it or downgrade the ADR's language from derived to declared.

### K3S-012 — The progress deadline is set to exactly the startup budget it is supposed to outlast
Severity: Major
Confidence: Certain
Target: `src/deployment/render/workloads.ts:56`; `spec/v1/20-resolved-deployment.md:140`; `docs/adr/0008:18-24`

Evidence:
```
    if (workload.image.tag === "latest") spec.progressDeadlineSeconds = 600;
| `progressDeadlineSeconds` | `startupBudget` | budget × 3, floored |
```

Problem: The spec says the deadline is three times the startup budget, and shows `1800` against a `600s` budget (`:238`, and `10-service-intent.md:363` declares `startupBudget: 600s`). The renderer emits `600` — and only for `latest`-tagged images; every other workload gets no field at all, which is the Kubernetes default of 600. ADR-0008 explains why 1800 was chosen: *"JVM cold start (~250–300 s); the 600 s startupProbe budget covers it"*. So the rendered deadline equals the startup probe budget rather than exceeding it.

Consequence: A JVM that cold-starts slowly — the case ADR-0008 says the tuning exists for — is still inside its legitimate startup probe window when the Deployment is marked `ProgressDeadlineExceeded`. Flux's health check on that Kustomization then fails, and because layers carry `dependsOn` (`fixtures/deployment/golden/cluster/flux/clusters/production/kustomizations.yaml:18`), every downstream layer stalls behind a rollout that was going to succeed. It presents as a deploy failure that resolves itself if you wait and retry, which is the shape of bug that gets a retry loop rather than a fix.

Direction: Whichever number is right, the deadline and the startup budget must not be derivable to the same value.

### K3S-013 — Deploy authority is namespace-granular, so the API-server control does not enforce the rule it exists for
Severity: Major
Confidence: Certain
Target: `spec/v1/examples/rendered/deployer-rbac.yaml:8, 22, 28-45`; `spec/v1/50-lifecycle.md:200-201`

Evidence:
```
# deploys: [auth-api, auth-ui]  ->  namespaces auth-system, app-system
  - apiGroups: [apps]
```

Problem: The claim is *"a workflow that tries to apply a Service it does not own receives a 403"* (`50-lifecycle.md:200`), and `spec/v1/50-lifecycle.md:93` says `deploys` is one-to-one across the estate. But the generated Role is per-namespace with no `resourceNames`, and this very file shows two Services resolving to a shared namespace (`app-system`, which `20-resolved-deployment.md:131` confirms is also `home-portal`'s aliased namespace). Any aggregator holding a Role in `app-system` can patch and delete every Deployment in it, including Services owned by a different aggregator. Separately, `create`/`patch` on `deployments` and on `secrets.hashicorp.com/vaultstaticsecrets` are each sufficient to read every Secret in the namespace: a Deployment can mount any Secret, and a `VaultStaticSecret` can name any Vault path the VSO role can reach and materialise it as a Secret. The Role withholds `secrets` verbs, which reads as a control and is not one.

Consequence: The one property that justifies Kubernetes here (see the section above) is weaker than advertised, and it is weaker in the direction that matters — `E_MULTIPLE_DEPLOYERS` is a CI check, not an API-server control, wherever namespaces are shared. The Vault reach is bounded by VSO's role rather than by the aggregator's `deploys` list, which means ADR-0005's per-service Vault policy derivation is bypassable by anything that can write a `VaultStaticSecret`.

Direction: Either namespaces are one-per-Service (making the Role granularity match the rule), or deploy authority needs an admission control rather than RBAC alone.

### K3S-014 — Pre-deploy hook Jobs are immutable, unretryable, never cleaned up, and gate a Flux layer
Severity: Major
Confidence: Certain
Target: `src/deployment/render/hooks.ts:37-59`; `src/deployment/render/flux-root.ts:82-95`

Evidence:
```
      backoffLimit: 0,
    metadata: metadata(hookName(workload, hook), workload.namespace, keelAnnotations(workload)),
```

Problem: The Job name is `${workload}-${hook}` with no content hash, and a Job's `spec.template` is immutable. When the hook's image or command changes, the apply is rejected with `field is immutable` — server-side apply does not recreate Jobs. `backoffLimit: 0` with `restartPolicy: Never` means one attempt: a transient `ghcr.io` pull failure fails the Job permanently. There is no `ttlSecondsAfterFinished`, so every completed Job and its pod accumulate, and no `activeDeadlineSeconds`, so a hung hook hangs indefinitely. `mergeWaits` then sets `layer.wait = true` and adds the Job to the Kustomization's `healthChecks`, and layers carry `dependsOn`.

Consequence: One flaky image pull — the failure mode ADR-0008 explicitly cites as having taken a service down — permanently fails a Job that a Flux layer waits on, which blocks every dependent layer until someone deletes the Job by hand. Changing a hook produces an apply that cannot succeed, with a Kustomization stuck `NotReady` and an error message about immutability rather than about the hook. Both failures are recovered only by `kubectl delete job`, on a single-node cluster, by hand.

Direction: A hook Job needs a content-hashed name and a retry budget before it is allowed to gate a reconcile layer.

### K3S-015 — The prune pass is a `kubectl get` that enumerates no custom resources
Severity: Major
Confidence: Likely (the pseudo-code is explicit; the `apply prune` implementation it stands for does not exist in this repository to check)
Target: `spec/v1/50-lifecycle.md:105-108`

Evidence:
```
prev = kubectl get -l deploy.jorisjonkers.dev/deployer=<aggregator>
for obj in (prev - curr):  kubectl delete …          # prune
```

Problem: `kubectl get -l <selector>` with no resource type returns the default resource set for the namespace — pods, services, deployments, and so on. It does not enumerate CRDs. Nothing in the shown inventory query names `ingressroutes`, `vaultstaticsecrets`, `servicemonitors`, `networkpolicies` or `persistentvolumeclaims`, and it is not scoped `--all-namespaces` either, while the deployer's own Role spans two namespaces. `spec/v1/50-lifecycle.md:122` builds the whole prune design on this — *"The cluster is the inventory"* — and `:130` names the only residual risk as a drifting label.

Consequence: The objects that never get pruned are exactly the dangerous ones. A withdrawn route leaves its `IngressRoute` in place, so a hostname stays publicly served after the Service that owned it is gone — and with `allowCrossNamespace: true` on both Traefiks (`traefik-public/release.yaml:34`) it can still point at a live backend. A withdrawn secret grant leaves its `VaultStaticSecret` reconciling, so VSO keeps refreshing a Secret nobody audits. Both are invisible to the delete pass forever, and `:127` has already trained the reader to expect orphans as normal.

Direction: The inventory query has to enumerate the same kinds the adapters render — that list already exists, in the deployer Role.

### K3S-016 — Durability Class, the backup job and the off-cluster copy exist only in prose
Severity: Major
Confidence: Certain
Target: `docs/adr/0008:59-65`; `spec/v1/20-resolved-deployment.md:151`; `src/deployment/render/`

Evidence:
```
It is replaced by a Durability Class per volume — `reconstructible`,
| backup job and retention | `volumes[].durability` | `reconstructible` renders none |
```

Problem: ADR-0008's central argument is that `rollbackTargetRetention` was *"an inert attestation"* — validated, scorecarded, documented as failing *"never"*, and *"read by no renderer or adapter"* — and that a Durability Class replaces it because it **renders**. A repo-wide grep for `durability`, `reconstructible`, `recoverable`, `irreplaceable` and `backup` across `src/` and `schemas/` returns **zero hits**, and `src/deployment/render/` has fourteen files, none of which is a backup renderer. The mechanism that distinguishes the new field from the old one has not been written.

Consequence: Until that renderer exists, `durability: irreplaceable` is exactly what `rollbackTargetRetention` was — a field an owner sets, a scorecard reads, and no object anywhere reflects. Given K3S-001 (no PV snapshots, no datastore backup, single node) the estate's entire data-durability story is currently one unimplemented derivation, and the ADR's own standard for what makes an attestation worthless applies to it verbatim.

Direction: The ADR should say the derivation is proposed; the `60-setup.md` checklist should not permit a first production apply of an `irreplaceable` volume before it exists.

### K3S-017 — The drift CronJob stops permanently and silently after downtime
Severity: Major
Confidence: Certain
Target: `spec/v1/examples/rendered/reapply-cronjob.yaml:19-34`

Evidence:
```
  schedule: '23 * * * *'
  concurrencyPolicy: Forbid
```

Problem: The CronJob has `concurrencyPolicy: Forbid` and neither `startingDeadlineSeconds` nor `activeDeadlineSeconds`. The CronJob controller stops scheduling entirely once it has missed more than 100 start times with no starting deadline set, and it does so by setting a condition that nothing here watches. Separately, `Forbid` plus no active deadline means one hung re-apply blocks every subsequent run indefinitely. The container also carries no `resources` (BestEffort, first evicted under the node pressure K3S-003 makes likely) and a mutable image tag, `:1.0.0`, in a design whose own rule is *"a digest, never a tag"*.

Consequence: This is the estate's only continuous drift correction — `spec/v1/50-lifecycle.md:145` argues it exists precisely because *"drift correction is a reaction to something having gone wrong"*. Four days of node downtime, or one wedged run, and it stops forever with no alert, because nothing alerts on a CronJob that is not firing. The cluster then diverges from its lock silently, which is the exact condition the CronJob was introduced to make impossible.

Direction: A drift corrector needs a deadline, a timeout, and an alert on its own absence — its failure mode is silence, which is the one thing the rest of this design is careful about everywhere else.

### K3S-018 — Sidecars and init containers lose their volumes, ports, probes and resources
Severity: Minor
Confidence: Certain
Target: `src/deployment/render/workloads.ts:177-192`

Evidence:
```
function containerLike(item: ContainerModel): KubernetesObject {
  if (item.command && item.command.length > 0) result.command = [...item.command];
```

Problem: `containerLike` renders name, image, pullPolicy, command, args and env — and nothing else. Ports, `volumeMounts`, `envFrom`, probes and `resources` are all present on `ContainerModel` and all dropped. `podTemplate` routes every sidecar and every init container through it, while the primary container goes through the much fuller `container()`.

Consequence: The three sidecars `spec/v1/10-service-intent.md:504` names as the motivating cases break in different ways. `postgres-exporter` on 9187 gets no port, so the `ServiceMonitor` that `validateWorkload` insists must reference a declared port has nothing to bind to. An init container that prepares a volume gets no mount and writes into its own ephemeral filesystem — succeeding, and doing nothing. The `sidecars` field is `<<proposed>>` in chapter 10, so this is a gap to close before it is graded rather than a live defect.

Direction: One container renderer, not two.

### K3S-019 — Two different default Vault addresses, both plaintext HTTP
Severity: Minor
Confidence: Certain
Target: `src/deployment/render/vso.ts:5`; `src/adapters/flux-utils.ts:694`

Evidence:
```
const DEFAULT_VAULT_ADDRESS = "http://vault.vault-system.svc.cluster.local:8200";
    VSO_DEFAULT_VAULT_ADDRESS: "http://vault.data-system.svc.cluster.local:8200",
```

Problem: The deployment renderer's `VaultConnection` default and the Flux pack's VSO default name **different namespaces** for the same Vault. One of them points at a Service that does not exist. Both are `http`, so every secret in the estate — ADR-0005's entire `delivery: env` and `delivery: file` surface — crosses the pod network in cleartext, on a cluster whose default CNI does no encryption.

It sits next to `spec/v1/00-overview.md:158`, which already flags that secrets-at-rest encryption is not configured either — so secrets are unencrypted in flight and at rest.

Direction: One default, and it should not be `http`.

### K3S-020 — Topology spread renders as the silently-ignored preference ADR-0009 exists to ban
Severity: Minor
Confidence: Certain
Target: `src/deployment/render/workloads.ts:364-371`

Evidence:
```
      whenUnsatisfiable: "ScheduleAnyway",
```

Problem: `whenUnsatisfiable: ScheduleAnyway` means the constraint is advisory: the scheduler scores it and then places the pod wherever it likes. `docs/adr/0009:43-46` builds its whole capability vocabulary on rejecting exactly this shape — *"A `prefers` that cannot be met is discarded by the scheduler in silence, which is why an unsatisfiable preference is a **build error** here rather than a runtime shrug."* On a one-worker cluster, a hostname spread is unsatisfiable by definition and always discarded.

Consequence: Someone reads `topologySpreadConstraints` in the rendered manifest and believes replicas are spread across nodes when they are co-located on one. That is the `gpu-model-gtx960m` failure the ADR quotes verbatim — *"it read as GPU-aware placement while doing nothing"* — reproduced by the renderer in the same release as the ADR that condemns it.

Direction: If soft preferences must be build errors when unsatisfiable, this one is not exempt.

### K3S-021 — HPAs are rendered against Deployments that also carry `spec.replicas`, targeting utilisation of requests that may not exist
Severity: Minor
Confidence: Certain
Target: `src/deployment/render/autoscaling.ts:33-52`; `src/deployment/render/workloads.ts:45`

Evidence:
```
    replicas: workload.replicas ?? 1,
      minReplicas: workload.autoscaling?.minReplicas ?? 1,
```

Problem: The Deployment always carries an explicit `spec.replicas`, and the HPA is a separate object scaling the same field. Under a reconciler that re-applies the manifest — Flux for class B on its interval, and the hourly re-apply CronJob for class A — `replicas` is written back to the manifest value on every pass, fighting the HPA. Independently, the HPA's only metric is `Resource`/`Utilization`, which is a percentage of `requests`; per K3S-003, `resources` is frequently absent.

Consequence: Two failure shapes, both quiet. With requests present, the pod count oscillates on the reconcile interval and is diagnosed as flapping load. With requests absent, the HPA reports `<unknown>/70%` and never scales at all — an autoscaler that is present, `Ready`, and inert. `fixtures/deployment/golden/.../workload.yaml:107-122` shows exactly this pairing: `replicas: 2`, an HPA with `minReplicas: 2`, and a container with no `resources`.

Direction: A workload is scaled by the HPA or by the manifest, and the renderer knows which.

### K3S-022 — `fixtures/deployment/golden/` is an orphan tree of manifests the API server would reject
Severity: Minor
Confidence: Certain
Target: `fixtures/deployment/golden/cluster/flux/apps/stateless/web-api/workload.yaml:30-32, 39-43, 63`

Evidence:
```
          volumeMounts:
```
